When does A* save work?

Dijkstra and A* on grids with obstacles and on the California road network. They return the same shortest paths, but do very different amounts of work to find them.

Elnur Haqqverdiyev · Rajab IskandarliM1 Data Science and Artificial Intelligence

The question

Both algorithms return the same shortest path. The difference is how much of the graph they look at.

Measure 1 · work

Expanded vertices: how many vertices the search settles before it reaches the target.

Measure 2 · cost

Wall-clock time: nanoseconds around one search call, median of repeated runs.

Comparison

Always paired: both algorithms run on the same graph, the same source and target. Ratio = Dijkstra ÷ A*, so above 1 means A* wins.

time = expansions × cost per expansion

So A* is faster only when

expansions(Dijkstra)expansions(A*) > cost(A*)cost(Dijkstra)

One A* expansion costs 1.2 to 2.0× a Dijkstra expansion in our runs: for every vertex it settles, A* pushes more entries into the heap and computes h for each of them. The rest of the talk is about when the left side is bigger.

How Dijkstra searchesillustration · 63 × 35 grid

Dijkstra settles vertices in order of distance from the start

Dijkstra f = gsettled0

Priority f(v) = g(v), the distance walked so far. The closest unsettled vertex is always next.

The frontier grows like a ripple, the same in every direction. Dijkstra has no idea where the target is.

pop u with the smallest f
if u is already settled: skip it
if u is the target: stop
for each neighbour v of u:
  if g(u) + w(u,v) < g(v):
    g(v) = g(u) + w(u,v)
    push v with priority f(v)
settledwaiting in the heapshortest path
How A* searchesillustration · same grid, same start and target

A* adds a guess of the remaining distance

A* f = g + hsettled0

Priority f(v) = g(v) + h(v): distance walked plus a guess of what is left, so f estimates the whole path through v. On a grid the guess is Manhattan distance: steps left or right plus steps up or down.

h to the target ◎ · outlined cell: h = 8, and with no walls the true distance is also 8

It never overestimates, so A* still returns the exact shortest path. It changes by at most 1 per step, so no vertex is settled twice.

Ties in f are broken toward the larger g (larger_g): keep walking the path you are on.

What we measuredfrozen protocol · PROTOCOL.md

Five grid structures and one real road network

Grids

Each family at 128², 256², 512² and 1024² cells, 4-neighbour, unit cost.

Road network

SNAP roadNet-CA: 1,957,027 intersections, 2,760,388 road segments, unit hop cost.

One search routine

Dijkstra is the A* code with h = 0: same heap, same loop, same counters.

Queries

15 per grid, 30 on roads, in short, medium and long distance bands chosen by BFS.

Treatments

Grids: Dijkstra, A* (larger_g), A* (node_id). Roads: Dijkstra, ALT with K = 1, 4, 8, 16. 3,600 timed runs.

Correctness

3,600 of 3,600 runs matched an independent BFS distance. No timeouts.

Fewer expansions ÷ costlier step predicts the measured speed-up within 13% in every case. In the maze the first number is 1.02, so the extra cost per step decides the result.

Why a step costs more: for each vertex it settles, A* pushes 1.6 to 3.0 heap entries (Dijkstra: 1.0) and computes h for each one. These are neighbours at the edge of its narrow search that it never settles. Open grid: 3.0 pushes, 2.03× cost; maze: 1.0 push, 1.21×.

Grid sizetime ratio Dijkstra ÷ A*, 15 queries per point, log scale

The open-grid win grows with size; walls cap it

On the open grid Dijkstra's work grows with the area (about 2d² cells for distance d) while A* grows with the path (about d cells), so the ratio grows like d: 45× at 128², 390× at 1024². Eight times the side gave 8.6 times the ratio.

With walls the ratio stays between 8× and 34× at every size: detours keep the A* search wider than one path. The maze approaches 1 but never crosses it in the median.

Road network · the heuristicALT = A*, Landmarks, Triangle inequality

Roads have no grid coordinates, so landmarks give the lower bound

Before any query: pick 16 landmarks far from each other and store the BFS distance from each landmark to every vertex (16 × 1.96 M numbers, 125 MB).

Triangle inequality: going from L to v through t is never shorter than the shortest route, d(L,v) ≤ d(L,t) + d(t,v), so d(v,t) ≥ d(L,v) − d(L,t).

h(v) = max over landmarks |d(L,v) − d(L,t)|

It never overestimates and is consistent, so A* still returns the true shortest path. The experiment uses the first K = 1, 4, 8 or 16 landmarks; every h(v) reads K table entries.

More landmarks, more savings, with no plateau at 16

K = 1 halves the expansions, but the time gain is small: not significant here (p = 0.13), 1.41× with p = 0.007 on the second machine.

K = 16 vs K = 8 on the same queries: 21% less time and 25% fewer expansions (p < 10⁻⁴). The predicted plateau did not appear.

Long queries (K = 8): Dijkstra 448 ms, A* 99 ms.

Exploratory · what makes a heuristic informative300 grid queries · error measured on 5,000 sampled vertices each

Admissible is not enough: the guess has to be close

Heuristic error = mean |true distance − h| ÷ mean true distance, from a reverse BFS from the target.

Spearman correlation with the speed-up: −0.81 (−0.83 on the second machine). A straight-line fit on this one number explains 55% of the spread in log speed-up.

Maze: error 0.97, so h is almost useless. Roads with ALT K = 8: error 0.155, rank correlation with the true distance 0.98.

Exploratory · weighted A* in perfect mazesoriginal run · f = g + ε·h · time ratio Dijkstra ÷ weighted A*, 15 queries per point

In large mazes a greedier A* wins, and the path stays optimal

Multiplying h by ε makes A* chase the target harder. It loses the guarantee of a shortest path.

A perfect maze has exactly one route between two cells, so the path cost stayed 1.00 at every ε.

At 1024², ε = 50 is 1.68× faster than Dijkstra (short queries 3.43×). At 128² it was still slower (0.86×), but 1.14× faster on the second machine, so the small-maze result is not stable.

With alternative routes, ε would trade path length for speed.

Exploratory · many queries at once5 grids at 1024² + 30 road queries · 270 tasks per batch

Parallel batches: throughput scales, the A* advantage holds

Each search stays sequential. OpenMP hands whole queries to threads, each with its own scratch memory and heuristic.

16 threads: 9.73× throughput (61% efficiency) on the original machine; 12 threads: 7.18× (60%) on the M4 Pro.

The median Dijkstra ÷ A* time ratio stays put under load: 14.8× → 17.9× and 14.6× → 15.4×. The maze stays below 1.

Where the conclusions stop

One real graph, hop countsSNAP gives no road lengths or travel times. Weighted routing could behave differently.
Synthetic gridsEach family isolates one structure. They are controls, not a sample of real maps.
Two-way roadsThe road graph was symmetrised; one-way streets are not modelled.
One implementationBinary heap with lazy deletion for both. Another priority queue changes the constant per step.
Few queries per cell5 to 10 queries per size and distance band. Effects at that level did not replicate; only family-level results are claimed.
Wall-clock timeAbsolute times depend on the machine; paired ratios, medians, bootstrap intervals and a second machine are the defence.
The answerT01 · When does A* save work?

A* saves time when its heuristic removes more expansions than it adds cost to each one.

SituationUseEvidence
Open or lightly obstructed gridA*, Manhattan12.8× to 106× faster
Rooms, clustered obstaclesA*, Manhattan8.7× to 12.8× faster
Road network with 8 or more landmarksA*, ALT7.6× (K = 8) to 13.5× (K = 16) faster
Perfect maze, long winding corridorsDijkstraA* is 24% slower; weighted A* helps only on large mazes
